# Interpret Davinci Dashboard

用真实数字回答，把事实和可能原因分开，不虚构机制。

## 启动

解读只用常驻的只读工具（`dashboard.get_structure` / `get_widget_config` / `get_widget_data`），不需要 ToolSearch，也不调用任何写工具。

## 工作流

1. **先口径，后数值。** 读结构 → 按 widgetIds 批量读目标配置与数据；可在同一回复并行两个只读工具，拿齐口径和数值后再解释。用户消息末尾若有 `<davinci_context name="dashboard_structure">`，那就是当前结构，直接用；只有它缺失或 `resourceRevision` 变了才调 `dashboard.get_structure`。没读口径就报数字，等于在报一个不知道含义的数。
2. **界定范围。** 默认只读用户问到的 Widget，加上口径上确实相关的对照项。整体解读使用现有 widgetIds 批量读取，不逐个续接。
3. **陈述事实。** 每个数字都带上它的口径（时间范围、筛选、聚合）。同环比按页面标签转述：`diffRate` 是差异率、`diff` 是差值。
4. **提出假设。** 异常点单独成段，写成「可能原因 + 用什么下钻可以验证」，不要写成已确认的结论。
5. **交回结论。** 结论先行 → 异常点 → 建议的下一步下钻。需要改配置时，说明建议并等用户明确要求，本 Skill 不写入。

## 数字纪律

- 存在 metadata.dailyChangeSummary 时优先使用其最大绝对变化、最大比例变化及日期，保留正负方向；百分比前值必须大于 0。范围只限本次返回数据，不外推全量。缺摘要时按已有数据解释，不额外猜日期粒度。
- **只报工具返回的数字。** 自己算的派生量（占比、日均、差额）必须写明算法，且只能用返回值做输入。
- **不推演平台如何计算。** 同环比、时间窗口的计算方式由平台定义：`last_days`（最近 N 天）下**日环比 `dayChain`、周同比 `weekSame`、年同比 `yearSame` 都是合法组合**，月环比 `monthChain` 不可用。看到「最近 7 天 + 日环比」不要断言配置自相矛盾，更不要据此反推每天各是多少。口径是否可用以平台规则和工具回执为准。
- **截断不是总量。** `pagination.truncated:true`、`rows.length`、`maxRows` 都只说明读回样本被裁；总数只有 `metadata.total` 存在时才算数。不要用样本行数推算订单量、客单价或业务规模。
- **数据缺失如实说。** 没有时间序列就说看不出趋势，不要用单点数字描述走势。
- 导航成功与取数成功分开报告。`QUERY_FAILED` 只证明该组件本次查询失败；字段齐全不能证明配置正确，一次刷新仍失败也不能排除临时故障。按已知错误定位，不擅自改表或口径。

## 红旗 —— 出现就停下

- 想写「平台通常会这样计算……」→ 停。你不知道，也不需要知道；只报口径和数字。
- 想从一个比率反推出未返回的明细数字 → 停。那是编造。
- 想说「配置有问题/口径错了」→ 先核对平台规则；`last_days` + 日环比是合法的。
- 想调 `apply_widget_spec` / `publish` 去「验证」或「修正」→ 停。解读任务零写入、零发布。
- 想用样本行数说业务规模 → 停。

| 借口 | 事实 |
|---|---|
| 「用户问出没出问题，得给个判断」 | 给判断可以，但只能基于返回的数字；证据不足就说清缺什么。 |
| 「推一下平台算法能让解释更完整」 | 完整但可能是错的。基线里正是这一步把一个合法看板说成了坏的。 |
| 「顺手把口径改对」 | 解读不写入。说明建议，等用户要求。 |

## 输出形态

结论先行的一段话 → 事实（数字 + 口径）→ 异常与假设 → 建议的下钻。不复述工具过程或 JSON 字段名；用「日变化摘要」说明工具提供的变化数据。
